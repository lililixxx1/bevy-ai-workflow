## 一、选品逻辑与硬标准对照

选品逻辑（§8 原文口径）：**什么品类最能锻炼并验证这套工作流**，而非最想玩什么。五条硬标准落到可执行筛选：

| # | §8 硬标准 | 可执行筛法 |
|---|---|---|
| 1 | 离散/回合制优先，确定性模拟（可种子重放） | 游戏循环必须是「玩家动作 → 离散结算 → 新状态」；实时仅允许出现在表现层（动画/音效），不进规则面；随机源全走种子（repo 已有 `SplitMix64`，`game/src/rng.rs`） |
| 2 | 游戏状态可经 BRP 查询并断言 | 核心规则状态全量存 ECS 组件/资源，`world.query` / `game.run_tests` 可断言；胜利条件是**状态断言**而非人工目测；表现层不作验收面 |
| 3 | 避开实时动作/物理手感、强叙事演出 | 排除：平台/动作/射击/竞速、物理手感调优类、叙事冒险/演出驱动类 |
| 4 | 中小体量 | 以系统数 + 日历周 + 测试集新增任务数三重封顶（§四），超限触发范围复审 |
| 5 | 达标候选池（示例非封闭） | 回合制策略 / roguelike / 解谜 / 离散 tick 模拟经营 |

确定性口径细化（本文追加，供 §二各案沿用）：规则面伤害/结算取整数运算，不引入浮点累积（跨平台可复现的基础）；「可种子重放」= 同关卡 + 同种子 + 同操作序列 → 状态序列逐位一致。两条落地纪律：① **迭代序**——依赖次序的规则逻辑一律按业务键排序/寻址，不依赖 query 迭代序（PIT-B-010：迭代序不保证，实测非插入序）；② **RNG 取数**——`SplitMix64` 现提供整数形态 `next_u64`（`game/src/rng.rs:13`）与浮点形态（`next_f32` / `next_range_f32` / `phase_hash`）；规则面抽取一律走整数映射（`next_u64` 取模/比例），浮点形态仅表现层使用。

## 二、候选案

### 候选 A：网格回合制战术小品（推荐）

**玩法概述**：9×9 网格，玩家小队 vs 敌方 AI，回合制「移动 + 攻击」，达成关卡目标（歼灭/占点）过关的关卡制战术。参照系是 Advance Wars / Into the Breach 的**离散结构**（非复刻玩法）：单位属性少、伤害结算确定、无实时元素。

**§8 逐条符合性**：① 回合制 ✓，敌方 AI 决策走 `SplitMix64` 种子（同种子同行为）；② 状态全 ECS（`Unit`/位置/HP/行动点/阵营、`TurnState`、关卡目标组件），布阵断言、结算断言、胜负断言三面俱备 ✓；③ 表现层（高亮/血条/动画）不作验收面 ✓；④ 系统面中等，三重封顶可控 ✓；⑤ 属「回合制策略」✓。

**系统清单（上限 10 席）**：① 关卡定义与加载（关卡即数据 → 逼出自研 RPC `game.launch_level`，见下）② 网格与占用 ③ 单位属性 ④ 回合机（阵营轮转/State）⑤ 移动与战斗结算（整数伤害公式）⑥ 敌方 AI（两级：种子随机 L1 / 贪心规则 L2——刻意不做行为树，防膨胀）⑦ 胜负判定（目标组件翻转）⑧ 表现层（网格渲染/选中/血条，UI 域）⑨ BRP 断言面（测试集任务化）⑩ 预留席：回放导出（操作序列日志，非持久存档）——owner 裁量可裁。

**工作流锻炼面（选它的核心理由）**：
- **逼出 `game.launch_level` 真实需求**：意向文档 §5.3 规划三方法中它至今未建（现役仅 `game.run_tests` / `game.screenshot` / `game.screenshot_log`，`game/src/rpc/mod.rs:38-43`；`docs/evidence/m2-rpc.md:142`「`launch_level` 未实现」）。关卡制游戏天然需要它——M4 首批任务即真实需求，不是造出来的练习题。

  > 注记（2026-09-28，M4 首任务 T032 后，原文未动）：`game.launch_level` 已落地（`game/src/rpc/launch_level.rs`，任务测试集 TS-13 六断言验证闭环）；本段「至今未建」系备忘录草案起草时点事实。另：§二 A 案「关卡以数据文件落地（BSN/结构化数据二选一由首任务定）」的实际裁定 = **代码内常量表先行**（先落关卡格式与加载语义，数据文件/资产加载形态推迟至后续任务），理由与记录见 `game/src/level.rs` 模块注释与 `docs/evidence/ts-13-brp.md`。
- **五个 M3 资产域全部压到**：ECS 查询/调度（C 批）、事件/State/回合机（D 批）、BRP 反射断言（E 批）、场景/资产加载——关卡以数据文件落地（F 批，BSN/结构化数据二选一由首任务定）、UI/渲染（G 批，恰是 G 批沉淀最厚的域）。
- **断言面举例**（全部可进 `game.run_tests`）：`launch_level(n)` 后查询布阵；玩家操作后 HP 变化与占位变化；`end_turn` 后敌方行动结果逐项断言；目标组件状态翻转 = 胜负；错误输入（坏实体/越界）走 `Result` 路径不击穿进程——最后一条直接吸收 M3 净新发现 PIT-B-051（BRP 坏实体裸 panic）的教训。

**三固化项草案（A 案）**：
- **可玩性定义**（M4 验收②展开）：3 个战役式关卡全部可从选关打到胜负结算（核心循环闭环：选关 → 玩家回合 → 敌方回合 → 判定 → 下一关）；全程进程无 panic，且自研 `game.*` 方法与游戏代码的错误路径不击穿进程（内置 `world.mutate_components` 的坏实体裸 panic 属上游 PIT-B-051，游戏侧规避并记录，不属本条验收面）；新增测试集任务全绿（核心任务回归）；同种子 + 同操作序列重放逐位一致——重放一致性由测试驱动承担（BRP 按操作序列重放并逐位比对状态），不依赖第⑩席回放导出（裁⑩不裁本条）。
- **体量上限**：系统 ≤10、日历周 ≤4、taskset 新增任务 ≤14。
- **占位美术/音效来源**：见 §五（通用）。

### 候选 B：推箱子变体 Sokoban+（保底）

**玩法概述**：关卡制推箱子 + 步数记录 + 撤销/重放。**§8 符合性**：确定性完美（无随机）、断言面完美（箱位集合即全量状态）✓✓；体量最小 ✓。

**系统清单（上限 6 席）**：关卡加载（`launch_level`）/ 网格与移动规则 / 箱位与终点判定 / 撤销与重放 / 表现层 / 断言面。同样逼出 `launch_level`。

**定位与短板**：规则引擎薄、无 AI、UI 薄——五批资产域仅触 C/F/G 的子集且深度有限，**对工作流的压力测试不充分**（M4 是工作流的终极测试，太薄则测试失效）。断言面虽完美，但任务多样性与系统交织度不足，错题本/模式库的「消费-生产」循环转不满。

**三固化项草案（B 案）**：可玩性 = 10 关全通 + 每关步数上限内通过（步数回归断言）+ 同操作序列重放逐位一致 + 全程进程无 panic 且自研 `game.*` 方法错误路径不击穿进程（同 A 案口径）；体量 = 系统 ≤6、日历周 ≤2、taskset 新增 ≤8；来源同 §五。

### 候选 C：种子化卡组构筑 roguelike（缓）

**玩法概述**：回合制卡牌战斗 + 种子化地图/掉落。**§8 符合性**：① 须 RNG 全纪律化走 `SplitMix64`（洗牌/掉落）——锻炼面恰在「RNG 纪律」，但纪律成本高；② 断言面中强（手牌/牌库/敌人状态全 ECS，但交互路径多、断言面散）；③ **边际冲突**：卡牌平衡是人工审美活，UI 交互最重（手牌/目标选择），人工验收占比升高，与 §8 第 3 条排除标准（「人工手感验收占比高」「人工审美验收占比高」即排除）边际相抵；④ 体量最易失控。

**锻炼面真实优势**：卡牌数据 = 资产/反射域深水（E/F 批），数据驱动设计吃得上。**结论：不推荐首发**；若 owner 选它，三固化项按以下写死：可玩性 = 种子通关一局（≥3 层）且卡牌效果与伤害结算经状态断言验证**规则正确**（**无平衡性验收**——平衡属人工审美，明确排除）+ 同种子同操作序列重放逐位一致 + 无 P0（同 A 案口径）；体量 = 卡池 ≤30 张、系统 ≤12、日历周 ≤5、taskset 新增 ≤16；来源同 §五。

## 三、推荐与理由

| 轴 | A 战术小品 | B 推箱子 | C 卡组 roguelike |
|---|---|---|---|
| BRP 断言面 | 强（布阵/结算/胜负三层） | 强（但状态简单） | 中强（面散） |
| 体量可控 | 中（封顶可控） | 高 | 低（易失控） |
| 工作流锻炼强度 | 高（五批域全压到 + `launch_level` 真实需求） | 低 | 高但带人工验收风险 |

**推荐 A**：三轴综合最优——断言面丰富度足以让「状态注入 > 截图」的验证哲学吃满，体量封顶可控，且把 M3 五批资产域（C/D/E/F/G）从首批任务起全部转为消费场景。**B 为保底**（owner 若求最快闭环）。**C 缓发**（若未来做，按其限制条款立项）。三案共同点：以「关卡/种子」为验证单元，天然适配 taskset 任务化（M4 验收③）。

## 四、体量上限与防失控条款（owner 可修订）

- **三重封顶**（以选定案的 §二草案为准）：系统数 / 日历周 / taskset 新增任务数。**系统数**以 §二各案席位表计（含断言面席与预留席）；**日历周**为挂钟周（起 = owner 拍板后首个 M4 任务，止 = 可玩交付验收；台账「耗时」字段为分钟粒度，不折算为周）。任一触顶即触发范围复审——沿意向文档 §4「未达标处置」口径执行：禁止默认放行，须 owner 明示裁决（返工 / 降标准（留痕记入变更记录）/ 终止）。
- **范围预裁剪**（M4 不做，防蔓延；沿 M3 计划预注册先例）：不做教程、不做设置菜单（窗口用默认配置）、不做持久存档系统（关卡与重放经 `launch_level`/操作序列重载）、音频非门槛（见 §五）、单一固定分辨率（沿帧率基线口径）。

## 五、占位美术/音效来源策略（三案通用）

- **主源：Kenney（kenney.nl）**。官方 FAQ 明示「all game assets on the asset pages are public domain licensed (CC0)」——商用可用、无需署名（核实于 2026-09-28，kenney.nl/support）。网格战术/推箱子/卡牌所需的 tile、棋子、UI 件与音效均有 CC0 合集可选用；具体包名在 M4 首个资产任务时选定（不在此凭记忆预写），随包 license 文件入库，来源与许可记入 `game/assets/CREDITS.md`。
- **备源（仅补缺）**：OpenGameArt（用 CC0 过滤器筛）、freesound（许可混杂，**逐件核**后入库）。
- **音频缺省策略**：M4「可玩交付」（意向文档 §4 M4②）不含音频要求——音效为加分项非门槛，缺省无声不阻塞验收；避免音频生产阻塞主线。
- 资产均为可公开许可，两层知识资产「不掺私货、保持可公开态」口径（意向文档 §6/§9）不受影响。
